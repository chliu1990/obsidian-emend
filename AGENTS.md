# Emend

## Project overview

This repository contains an Obsidian community plugin written in TypeScript and bundled with esbuild. The plugin provides context-aware, streamed AI chat for Markdown notes in explicit modes, guarded full-note editing in Edit mode, and guarded selected-text replacement. Closed JSON operations are the only model-facing edit protocol, returned as a bare array or as an envelope with an optional model-written summary; valid operations compile into the same internal CriticMarkup and Track Changes path.

The repository contains the completed Emend rewrite:

- The **current implementation and release identity are Emend**. `manifest.json` uses plugin ID `emend` and name `Emend`; `package.json`, `manifest.json`, `package-lock.json`, and `versions.json` carry consistent release metadata. This is a clean plugin ID with no Lapis Lazuli data migration.
- Ask, Discuss, and Brainstorm modes, instruction/skill loading, and streamed chat are wired into the current runtime. These paths have no note writer. DeepSeek `deepseek-flash` and `deepseek-v4-pro` additionally support default-off Review/Auto web research through a bounded model-directed search/fetch loop; Kimi/custom providers and other DeepSeek models do not.
- Edit mode sends the complete captured note and privately buffers the response. The Operations-only strategy atomically validates/compiles closed JSON operations, then Stage 07 revalidates the resulting markup before stale source/target guards and one `vault.modify` write. An optional model-written `summary` is attached only after that validation, shown in chat, and never written into the note. Applied results show the unchanged header, a `Target: Full note.` or `Target: Selection.` line, the optional summary, and bounded sanitized bullets; no-ops show exactly `No changes were needed.` plus an optional summary. Track Changes is the only review surface.
- The composer **Edit target** control defaults to Selection for usable selected text and Full note otherwise, with an explicit Full note override. Typed Edit and all three quick actions reuse the displayed target and one submission path; Selection failures cannot fall back to the full-note writer. Composer Selection captures exact offsets, sends the complete selection with default smart structural context or an exact Stage 09 symmetric opt-out plus the originating session's configured recent ready history, validates only the compiled annotated selection, and replaces only the captured range through `editor.replaceRange` for native undo. Ready chat keeps concise results, all-round usage, and successful-attempt reasoning in the originating session. The separate Modify Selection command captures exact offsets before opening its unchanged instruction modal, uses the same selection coordinator and native writer, and retains its existing notices without chat, usage, or retry-status displays. Operation targets cannot address text outside that selection.
- Composer, selection-modal, and coordinator capacity accounting is current behavior: each provider has optional context-window/output-reserve token settings with a persisted invalid marker, a compact bar below the chat mode controls and selection-modal title shows known input, remaining input, and a shrinking output allowance, and hover/focus floating details disclose the shared per-category character estimate and its exclusions. There is no composer meter, gray unknown segment, or compact-context button. Every submission is preflighted before networking with a per-fetch transport guard for later Web and correction rounds. This behavior adds no additional-note/instruction estimation, compression, tokenizer, new provider call, new vault read, or invented model limits.
- The dormant diff module, editor extension, callbacks, styles, and CodeMirror dependencies are removed.

The manifest requires Obsidian `1.11.4` or newer and sets `isDesktopOnly` to `true`. The streaming provider transport uses desktop browser `fetch` and Server-Sent Events; mobile support is not currently declared.

## Technology stack and build process

- TypeScript with strict compiler checks; source files are under `src/`.
- Obsidian API for plugin lifecycle, workspace views, Markdown rendering, settings, vault access, and notices; browser `fetch` and Server-Sent Events for provider streaming.
- esbuild bundles `src/main.ts` into a CommonJS `main.js` at the repository root, targeting ES2021.
- Obsidian, Electron, CodeMirror/Lezer modules, and Node built-ins are external to the bundle and supplied by the host. Other runtime code must be bundled; do not add unbundled runtime dependencies.
- Development builds include inline source maps and are unminified. Production builds are minified and have no source map.

### Commands

Use npm from the repository root:

```bash
npm install
npm run dev
npm run build
npm run lint
npm test
```

- `npm install` installs the dependencies in `package.json`. Use `npm ci` with the committed `package-lock.json` for reproducible installs and CI.
- `npm run dev` starts esbuild in watch mode and writes `main.js`. It does **not** run TypeScript type checking; use the production build or `npx tsc -noEmit -skipLibCheck` for that check.
- `npm run build` runs `tsc -noEmit -skipLibCheck` and then creates the production `main.js`.
- `npm run lint` runs ESLint over the project using the typed `typescript-eslint` setup and `eslint-plugin-obsidianmd` recommended rules.
- `npm test` runs Vitest once; `npm run test:watch` starts watch mode. Tests use the `obsidian` mock alias and must not access a real vault or the network.

`main.js`, source maps, `node_modules/`, `test_vault/`, and Obsidian's local `data.json` are gitignored. Do not commit generated bundles, vault content, mock credentials, or local plugin settings.

## Current runtime architecture

### Target note and request context

`main.ts` targets the active Markdown view when available. If focus is in the chat sidebar, it uses the last active still-open Markdown view, then falls back to another open Markdown view. `captureChatContext()` synchronously captures the target `TFile`, full source text, selection offsets, note label, optional vault-qualified path, and bounded Markdown before instruction reads or networking.

Read-only requests include bounded Markdown context. Notes within the configured character limit are sent whole; longer notes are windowed around the selection or caret, with `[...]` markers at omitted edges and unused budget redistributed toward available text. The default limit is 12,000 characters and the settings UI enforces a minimum of 1,000. Full-note Edit ignores the bounded `markdown` window and always sends `sourceText`. Modify Selection always sends the complete selection. Smart selection context defaults on and expands to containing paragraph(s), complete document-leading YAML, and complete fenced code before adding whole adjacent blocks within the source-character budget; oversized containing blocks use symmetric marked truncation without changing the target. Disabling it restores Stage 09 symmetric before/after context, including empty surroundings for an oversized selection. Vault name and note path are opt-in and disabled by default.

Additional notes are chosen only through the explicit **Add notes** Markdown picker. The in-memory store keeps ordered paths per target note, deduplicates the active note and repeats, shares selections between chat and Modify Selection for that target, and never shares them across different targets. Selections survive target-note switches during the current plugin session, clear on plugin or Obsidian reload, and are never persisted. Vault rename events update selected/target paths; open pickers and Modify Selection resolve the captured target `TFile`'s live path, and controls close their owned picker on destroy. Delete events remove deleted included paths. A missing-path race rejects the entire capture before any selected-note read, instruction read, or provider request. Opening the picker lists vault Markdown paths; selecting/opening/switching notes performs no content read or provider request.

At submission, coordinators capture the selected path array before their first await and resolve/read fresh selected-note content. Additional notes use a separate combined `maxContextCharacters` source budget: each note receives `floor(remaining budget / remaining notes)`, included source characters are subtracted, and unused capacity rolls forward. Capture begins at source offset zero because no additional-note caret/selection exists; omitted suffixes end with an exact `[...]` marker. Labels, prompt fences, and markers are additional to source-character accounting. Each snapshot's outer prompt fence is longer than its longest backtick run. Each separately numbered prompt section says the notes are read-only and not edit targets. With path sharing off, no source/basename/vault path label or metadata is added to the additional-note prompt; with it on, a `Path: <vault>/<note path>` line is included. Note content itself is preserved within the captured budget. Frontmatter, wikilinks, fenced code, math, Unicode, and empty files pass through unchanged within the captured budget. These snapshots never become write targets in any mode.

### Context capacity and draft estimates

1. Each provider stores nullable `contextWindowTokens` and `outputReserveTokens` plus a persisted `contextCapacityInvalid` marker. Both empty with no marker means capacity checks are off; both positive integers with `window − reserve > 0` are valid and clear the marker; one missing value, `window === reserve`, or `reserve > window` keeps the present values and marks the pair invalid; malformed values (string, `0`, negative, non-integer) are dropped to `null` while a valid sibling is kept and the marker is set; both cleared with a persisted marker stays invalid. Any settings edit re-resolves the full pair. Emend infers and fetches no limits and applies none automatically. An explicit **Use documented defaults** click is available only for DeepSeek `deepseek-flash`/`deepseek-v4-pro` at `1048576`/`393216` (1M context, 384K maximum output) and Kimi `k3.1-pro` at `1048576`/`131072` (up to 1M context on eligible plans and 131,072 default output; lower-tier plans may need a smaller window). These documentation values are not account-specific provider responses. Custom/unknown models remain manual, existing values change only on the click, and no metadata, pricing, tokenizer, or capacity provider call is added. Effective input capacity is `contextWindowTokens − outputReserveTokens`; the output reserve is local accounting only and is never sent as `max_tokens`.
2. `countRequestCharacters` sums UTF-16 lengths for the system prompt, user prompt, formatted history, tool continuations (including tool-call names and serialized arguments), and stringified tool declarations; duplicates across categories count at each occurrence. `accountRequestCharacters` estimates `max(1, ceil(chars / 4))` per nonempty category and sums them, so a multi-category request can estimate above `ceil(total / 4)`. This is a predictive approximation, not a tokenizer or billing data; completed-message usage semantics are unchanged.
3. Read-only, full-note, and Selection coordinators call `requireValidContextCapacity` before any await or read, then re-check the assembled request after fresh additional-note and instruction reads and an abort check, using `>=` capacity. `requestAiResponse` repeats the check at every fetch as `kind: 'transport'`, covering later Web main rounds, extractor/verifier/refine rounds, and the one Edit correction round. Abort checks precede capacity checks, so Stop wins. `unconfigured` never blocks; invalid settings throw the settings warning; over-capacity throws `This request needs about N input tokens, at or above the M-token input capacity.` plus kind-specific guidance (`Use a smaller selection.` for full-note, `Select a smaller target.` for Selection, read-only or transport remedies otherwise). Capacity errors are terminal for that submission: no retry, no correction, no Web/reader degradation, no partial answer, no write; chat shows the error, persists no assistant content, keeps the already-ready user prompt as with other failed requests, and releases the pending lock for retry.
4. The chat **Draft estimate** uses `buildReadOnlyDraftEstimate`, `buildFullNoteDraftEstimate`, or `buildSelectionDraftEstimate`, which reuse the submission prompt assembly (bounded read-only Markdown, complete note source, complete selection with the configured smart/symmetric context) and the configured ready-history window; the modal estimates its history-free selection request. It excludes loaded instructions/skills, additional-note contents, the first Web round's system prompt and tool declarations, and later Web/correction rounds. A slim focusable bar sits below the chat mode controls and before messages, with no composer meter; the selection modal places the same bar below its title. For window `W`, reserve `R`, and estimated known input `I`, remaining input is `max(0, W − R − I)` and remaining output is `max(0, min(R, W − I))`; the right-hand output partition therefore shrinks above effective capacity. Segments cover only known system/draft/history/tools/optional-continuation input, free input, and output, use `max(W, I)` as their denominator, and include no gray unknown segment. Unconfigured and invalid states show no proportional bar or output partition. Hover/focus reveals floating details with estimated input, remaining input/output, effective capacity, window/reserve, per-category tokens, and `Remaining input is a lower-bound estimate. Excluded from this estimate: instructions and skills, additional-note contents, the first Web round's system prompt and tool declarations, and later Web or correction rounds; the exact submission check remains authoritative.` Category text uses the same colors as its corresponding bar segments. The meter uses `aria-labelledby` with the persistent summary rather than an `aria-label`, avoiding a duplicate native `Context capacity` tooltip. Pointer exit/focus loss hides an unpinned panel; click pins it, outside click dismisses it, and document Escape works after focus loss. Open details survive value refreshes. The root is non-live; the persistent summary is the only `role="status"`/`aria-live="polite"` region, labeled `Draft token estimate`, and the display has `is-valid`/`is-unconfigured`/`is-over-capacity`/`is-invalid`/`is-unavailable` states plus `Draft estimate unavailable.` when no target can be captured. There is no details button or compact-context/compression control. Invalid capacity uses the single `INVALID_CONTEXT_CAPACITY_MESSAGE` sentence for the display, settings warning, Notice, and capacity error.
5. The estimate refreshes on composer input, mode and Edit-target changes, note switches, `editor-change`/`editor-selection-change` (150 ms debounce), additional-note store changes, and every `saveSettings()`, which refreshes all open chat views without reload. It performs no vault scan, additional-note read, or provider request. A draft blocks only when settings are invalid or the estimate is at/above effective capacity: Send is disabled, each quick action whose own prompt estimate blocks is disabled, Enter/Mod+Enter show the block Notice instead of submitting, and every submission re-estimates before creating a message, so blocked attempts make no request, message, save, or write. A blocked submission refreshes the bar in place without a full render so the visible estimate and controls match the Notice; typing and settings-callback refresh errors render `Draft estimate unavailable.` instead of escaping. Blocking never truncates or compresses the request.

### Multiple chat sessions and runtime identity

1. Each note owns an ordered schema-3 session aggregate. The chat title region contains a native **Chat session** selector plus New, Rename, Delete, Move up, and Move down icon actions. Rename collapses/validates a manual title; Delete confirms with the target as plain text; Move buttons provide keyboard-accessible ordering and disable at boundaries. Controls disable while sending, thread-loading, or session-mutating, and management actions never call a provider.
2. The view keys drafts by exact `{notePath, sessionId}` nested maps and captures provider history only from the originating session's ready messages within `historyMessageLimit`. Same-note switches preserve mode, Web, explicit/automatic Edit-target choice, and additional-note selections while recomputing active-session capacity. Drafts, stopped/error/loading content, and additional-note selections never persist.
3. Missing, empty, malformed, and unsupported aggregates expose one cached runtime-only New chat. Opening does not write. New from a sole empty transient materializes/replaces it and transfers its draft; a failed-save transient with ready user messages is recovered before a second empty session is created. Rename/Submit materialize transients; every successful transient `createSession` immediately clears that exact ID and a same-ID per-note cache entry regardless of request currentness, while visible metadata/rendering remains identity-guarded. Transient Delete performs no adapter mutation. Actual reload clears transient caches and drafts.
4. Automatic titles derive locally from the captured prompt only when a ready assistant successfully persists, in the same atomic append. Manual titles never change automatically; user saves, management, Stop/error/abort/capacity/stale paths do not title. Titles collapse whitespace and are limited to 80 Unicode code points, with 79 plus `…` for automatic truncation.
5. Every request captures `{notePath, sessionId, generation}` plus its active-request object. Note/session transitions and close increment generation and abort/close Web review. Stale loads, streams, completions, save Notices, and `finally` cleanup cannot affect newer state. The assistant and eligible title persist before the visible loading message becomes ready. Full-note/Selection summaries and Web metadata append only to the originating session.

### Sequential edits and per-note request isolation

`main.ts` owns one pending-path registry shared by every chat session/mode and Modify Selection. After synchronous target capture and nonempty prompt validation, `withNoteRequest()` acquires the captured note path before instruction reads or networking. A second request for that path — including one from another session of the same note — rejects with exactly `Wait for the current Emend request to finish.`; different note paths can proceed independently. The single chat view also disables its own duplicate UI submissions and session controls while sending.

The submission captures mode and source before awaiting. Each sequential Edit therefore uses the latest complete annotated note as its source, preserves earlier Track Changes tokens, and sends only ready user prompts plus concise local Edit results as assistant history. Those results carry `local-edit-status` provenance, may include model-written summary prose, and are annotated as local outcomes rather than model responses; neither the result nor its summary is an instruction or permission. Full annotated responses remain private and are never persisted.

The pending path is deleted in `finally` only after the coordinator settles on success, provider error, validation error, stale failure, or abort. ### Structural Markdown edit safeguards

1. Backtick-containing replacements use whole-target CriticMarkup so code delimiters remain reviewable. Remove/replace/comment targets intersecting inline code must contain the complete span, and insertions must be outside it without extending delimiter runs; content-only/cross-delimiter targets fail with `inline-code-range` and the normal one-correction opportunity. Complete spans and larger targets containing complete spans remain valid. Matching stops at blank-line and actual block boundaries while preserving valid lazy multiline spans, inline HTML, and autolinks.
2. Any target intersecting fenced code, including comments and larger containing targets, fails with `fenced-code-edit`. Semantic guards cover containers and unclosed blocks. Separate Track Changes 2.3.0 compatibility ranges recognize only zero-to-three-space bare openers and exact closing runs, continuing through blank lines, prefixes, and different-length runs until the exact later bare delimiter or EOF. List-created shadows and longer top-level closers therefore reject, while top-level/blockquote following prose remains reviewable. Nested semantic openings inside other review shadows reject. Every `closingContentEnd` insertion before the original line ending rejects; insertion after the closing line ending remains safe.
3. `markdown-edit-guards.ts` handles CRLF, escaped delimiters, outer table whitespace, backtick/tilde fences, container structure/indentation, and block-level table termination. Tables allow only text edits wholly within one existing header/body cell. One replacement-compilation pass supplies actual `compiledText`; all Operations per original row compose at actual compiled offsets, with zero-width insertions at `insertionPoint`, before comparing original/actual annotated/accepted/rejected delimiter, outer-pipe, cell-count, and block identity. This covers minimized fragmentation, composed backslash parity, actual insertion offsets, and four-space/tab indented-code exits. Delimiter, row/column, spanning, CR/LF, unescaped-pipe, and true HTML/fence block-start changes fail with `table-structure-edit`; escaped pipes, ordinary text, inline HTML/autolinks, and invalid backtick-fence info remain safe. Occurrence resolution and existing range-isolation checks run first, followed by one replacement-compilation pass and composed structural validation using actual `compiledText`. One violation rejects the entire candidate before final CriticMarkup validation or either writer runs. These are targeted conservative scanners, not full CommonMark coverage.
4. Selection passes full-note text and absolute offsets through `prepareEditResponse` solely for structural classification. Occurrence resolution, permissions, compilation, and replacement still use only captured `selectedText`; structural context never expands the target.
5. Raw markup displayed while the cursor is inside a table cell is upstream Obsidian/Track Changes presentation, not claimed fixed; accept/reject byte correctness is the criterion. Comments before/after replacements showed no ordering bug and retain their existing semantics. Stage 38 records the 35-file/817-test gate and 66-scenario fixed-v4 real-Obsidian evidence with two environment-limited CRLF setups.

### DeepSeek online search

1. The composer **Web** selector offers **Off**, **Review**, and **Auto** only for read-only submissions; it defaults to **Off** per view and is disabled in Edit and while loading/sending. Changing it performs no request. Review/Auto are supported only for DeepSeek `deepseek-flash` and `deepseek-v4-pro`. Kimi/custom providers and other models fail with `Online search is only available for DeepSeek deepseek-flash and deepseek-v4-pro.`; they never silently become ordinary unsearched chat.
2. Enabled main-model requests add only `web_search` and `web_fetch` declarations with `tool_choice: 'auto'`. Each call requires a nonempty `extractionGoal` of 1–1000 Unicode code points alongside its query or URL. The model decides whether retrieval is useful, may request multiple calls and rounds, and may legitimately choose zero calls. Emend validates every proposal's closed arguments, executes accepted calls sequentially, and emits content only from the terminal no-tool round while forwarding main-model reasoning across rounds. The main-model chat transport has no retry; Search and Fetch each allow the single bounded immediate retry described in item 6. There is no raw fallback or alternative provider.
3. **Review** opens an editable query/URL/extraction-goal modal before every executable batch, revalidates edits, and preserves call IDs/tool names; closing or cancelling aborts. **Auto** skips only that review pause. The disclosure states that DeepSeek may derive arguments from note context, successful retrieval may be billed separately, every call uses an AI extractor that receives the current question and extraction goal for up to 6 extractor rounds plus a verifier and up to 2 refine rounds with possible separate charges, a transient Search or Fetch failure may be retried once, failed calls still count toward the configured call limit, and query/URL/outcome metadata is stored locally. Main model rounds contain ordinary context/history/additional notes/instructions, while retrieval endpoints receive only the validated query or URL.
4. `maxWebToolCalls` defaults to 8, normalizes finite values to integers clamped to 1–20, and caps executed Search/Fetch calls. An over-limit batch executes only the first remaining calls in model order; Review shows only those executable calls and uses their edited arguments. Continuation preserves every proposed call ID, reviewed executable arguments, original skipped arguments, ordinary selected outcomes, and small `call_limit_reached` outcomes for skipped calls. Skipped calls perform no Search/Fetch/reader work and gain skipped activities. Emend then forces exactly one terminal main-model request without Web tools, answering from current note/chat and successful evidence; further tool calls fail without retrieval. Ready answers may have no evidence but cannot invent citations. Chat appends exactly one singular/plural skipped-call incompleteness warning when the skipped count is positive and persists it as ordinary content; exact-limit completion has no warning. `maxWebContentCharactersPerCall` independently defaults to 20,000 and normalizes to 1,000–100,000. It caps each complete serialized Search/Fetch extraction payload, so `N` executed calls contribute at most `C × N` characters with no separate total cap. `measureWebContent` currently measures UTF-16 `string.length` behind a token-ready character-unit interface; it is not exact tokenization, and the character-based usage estimate is not provider billing data.
5. Every readable Search/Fetch result invokes exactly one same-provider/model extraction and verification loop. Canonical title/snippet/summary/content remains temporarily available without raw-size truncation, but the main answering model receives only actual source metadata plus verifier-supported claims with their exact quotes, or quotes-only evidence for a source whose claims did not survive verification, never raw retrieval or unverified AI-generated facts. The extractor receives the current typed question, extraction goal, target, and source catalog, with empty history and no note snapshot/path, instructions/skills, additional notes, or vault access. It may use only closed local literal grep and UTF-16 ranged-read tools, limited to 6 model rounds, 8 local calls per round, 24 local calls total, and 4,000 characters per local result; a malformed local call returns a bounded 200-code-point `{"error":{"kind":"invalid_local_call","message":...}}` tool result and continues the same loop instead of discarding the extraction, counting against the same bounds; excess calls beyond the remaining per-round or total allowance return `{"error":{"kind":"local_call_limit_reached"}}` without discarding inspected evidence, a per-round overflow alone continues so the model can retry, and total-cap overflow or a sixth round with calls produces one forced no-tools JSON answer request; only tool calls in that forced request are a limit failure. Output is parsed tolerantly: fenced or prose-wrapped JSON, unknown fields, individually invalid claims or quotes, and unknown or duplicate source IDs are ignored or dropped, and one same-provider correction round is allowed when the terminal output is structurally unparseable. A claim has trimmed 1–500-code-point text and 1–4 exact verbatim quotes of 1–1,500 code points each; deduplicated result-level quotes are the fallback. Claims are capped at 8 per source and 24 total before verification, and every verifier request, including after refinement, is capped at 24,000 serialized claim characters; claims outside that budget are neither verified nor refined and fall back to result-level quotes. One verifier request per pass, capped at 3 passes, receives only the question, goal, and numbered claims with their quotes (no target, note, chat, instruction, additional-note, or vault context) and may only mark support; rejected claims get up to 2 no-tools refine rounds, and unsupported or unverifiable claims fall back to quotes rather than `extraction_failed`. Claims, quotes, and verifier reasons are framed as untrusted external data, and the verifier/refine prompts forbid following instructions inside them. The main model synthesizes only from supplied claims, quoted evidence, and actual source metadata, and every final-answer claim must remain supported by that evidence. Only successfully represented actual normalized credentialess HTTP(S) URLs become stable `S1`, `S2`, ... citations.
6. Expected Fetch failures, including empty pages and target-site extraction/policy failures, return explicit unread tool outcomes rather than invoking a reader or failing the whole answer. The ready answer includes a deterministic unread-page/incompleteness warning. A non-abort extractor provider/format/limit failure returns only `extraction_failed`, excludes that query's sources, and contributes to exactly one aggregate warning: `Emend could not extract information from N web query. The answer may be incomplete.` or its `queries` plural. Verification failure never becomes `extraction_failed`: the loop stops with any verified claims collected so far or the extractor's quotes-only outcome. After the reader returns its verified outcome, the coordinator's single per-call cap fit drops trailing claims, then trailing evidence, then truncates the last quote to a verbatim code-point prefix marked `truncated`, then drops empty results, and emits `no_relevant_evidence` when nothing fits; it never fails a call for size or passes raw content through. Dropping a claim, a whole result, or an evidence quote sets a per-fit `omitted` flag that the coordinator accumulates as `omittedEvidence`, while ordinary chat always reports `false`; a quote-prefix truncation is not an omission and is marked only by `truncated`. A verified claim result keeps its extractor result-level quotes internally so fitting can degrade it to quotes when claims are dropped, and a `truncated: true` quotes-only result tells the main model that the prefix may not fully support its claim. All aborts cancel the whole submission. Search and Fetch each make one immediate retry, with no delay, backoff, or setting, only for a failure without an HTTP status, status `429`, status `500`–`599`, or an empty Fetch page; other statuses, including `403`/`404`, are not retried. A Search that still fails becomes a non-fatal `search_failed` outcome with a failed activity so the model can continue on other evidence, while a still-failing Fetch keeps its `fetch_failed` unread outcome. Each failure tool result is a bounded `{"error":{"kind":"search_failed"|"fetch_failed","reason":...,"httpStatus":...,"attempts":...}}` object in that key order: `reason` is `network`, `http`, or `empty`, `httpStatus` appears only for `http`, and `attempts` is 1 without a retry or 2 after the single retry. Provider messages, URLs beyond the existing activity target, headers, and credentials are never included. Search/Fetch HTTP `400`/`401`/`402`/`413` and aborts remain fatal and are never retried. Ready answers append one warning per condition in this order: unread pages, extraction failures, failed searches (`Emend could not complete N web search. The answer may be incomplete.`, with `searches` when N > 1), cap-fitting omissions (`Emend omitted some extracted evidence to fit the per-call output cap. The answer may be incomplete.`), then skipped calls. Failed activities carry transient `network` (no HTTP status), `http` (non-fatal status), `empty` (empty Fetch page), or `reader` (extraction failure) reasons plus their attempt count; rows render as `Failed (network)`, `Failed (HTTP <status>)`, `Failed (empty page)`, or reader labels, with `, 2 attempts` appended when a retry was used. None of these fields is persisted. Retrieved text never becomes instructions, skills, or a write target, and the read-only coordinator still has no writer.
7. Usage covers every main, extractor, correction, verifier, and refine model round, including failed requests recorded with an empty synthetic result. It is provider-sourced only when every round supplies a complete valid triplet; otherwise every round is estimated independently and the total is labeled **Estimated**. Extractor, verifier, and refine reasoning are neither displayed nor persisted, and their requests/results, extracted payloads, and evidence extracts remain transient. Only ordinary ready content, sanitized citations/activity, main reasoning, and usage persist. Retrieval, Search, and reader charges/token counts are not invented.

### Providers and settings

DeepSeek, Kimi, and custom providers all use one OpenAI-compatible streaming chat-completion transport in `provider-stream.ts`. The editable presets are DeepSeek model `deepseek-flash` at `https://api.deepseek.com` and Kimi model `k3.1-pro` at `https://api.kimi.com/coding/v1`. Each provider has an editable HTTP(S) base URL, API key, model, reasoning-effort setting, `requestUsage` compatibility toggle, and the optional context-window/output-reserve capacity pair. The toggle defaults on for DeepSeek/Kimi and off for custom. Requests use browser `fetch` with `stream: true`, `temperature: 0.3`, the configured `reasoning_effort`, and the originating session's configured `historyMessageLimit` recent ready history messages (default 8, normalized 0–50, `0` disables history). No `max_tokens` field is sent, so the output reserve never changes the provider request body. Base URLs are trimmed of trailing slashes before `/chat/completions` is appended. `stream_options: { include_usage: true }` is present only when `requestUsage` is true; provider rejection remains an error with no chat-transport retry, so users can disable the option. Reader extractor, correction, verifier, and refine requests additionally send `response_format: { type: 'json_object' }`; main Web loop rounds and ordinary chat requests do not. Content and reasoning deltas are emitted separately, with optional final token usage and a done event. Usage parsing requires a complete nonnegative integer triplet and preserves zero. Provider errors include HTTP status and available provider details without credentials. Every request, including each Web main round, extractor/verifier/refine round, and the correction round, passes the per-fetch context-capacity guard described above after the abort check and before `fetch`; a capacity error is terminal and is never retried or converted into a provider-format or extraction failure. Web-enabled DeepSeek rounds additionally send the two tool declarations, `tool_choice: 'auto'`, and any tool continuation messages; ordinary requests are unchanged. Only DeepSeek web retrieval uses separate JSON `POST <base URL with one /v1>/tools/search` and `/tools/fetch` calls. There is no `requestUrl`, Gemini/Claude transport, fallback provider, or automatic retry on the chat transport for provider failures. The bounded retry exceptions are the single immediate web Search/Fetch retry in `deepseek-web.ts` (retryable only for a missing HTTP status, `429`, `500`–`599`, or an empty Fetch page), the explicit Edit/Modify Selection candidate-validation round documented above, and the reader's single format-correction round documented above; each uses the same provider, and no correction is triggered by provider or write failures.

When valid provider usage is absent, chat coordinators estimate request and response tokens independently as `max(1, ceil(characters / 4))`, using system prompt, retained history, current user prompt, tool declarations/continuation content, response content, and reasoning. Web usage is provider-sourced only when every round has a complete valid triplet; otherwise all rounds are estimated independently and summed. Estimated total is prompt plus completion and is always labeled `Estimated`; it is not provider billing data. Web search adds no pricing, tokenizer, or model-metadata network calls.

Settings are loaded with `loadData()` and normalized against defaults. On first load, any legacy plaintext provider key is written to its exact `app.secretStorage` ID (`emend-api-key-deepseek`, `emend-api-key-kimi`, or `emend-api-key-custom`), cleared in memory, and saved back sanitized. Requests resolve each active provider's key through `getApiKey()` with per-provider in-memory fallback; masked settings inputs use `getApiKey()`/`setApiKey()`. Every `saveSettings()` serializes a deep sanitized clone whose three provider `apiKey` fields are empty, regardless of caller mutations, and refreshes every open chat view's capacity meter. Non-secret per-provider configuration including `requestUsage`, active provider, default mode, note-path inclusion, smart selection context, `historyMessageLimit`, context size, `maxWebToolCalls`, `maxWebContentCharactersPerCall`, and the capacity pair is stored locally in Obsidian plugin data. `historyMessageLimit` defaults to 8, floors finite values to integers clamped 0–50, and restores 8 for missing or malformed values; `0` disables history. The Web call setting defaults to 8, clamps finite values to 1–20, and uses the default for malformed values. The independent Web output cap defaults to 20,000 characters, clamps finite values to integers from 1,000 through 100,000, and restores 20,000 for malformed values. `contextWindowTokens` and `outputReserveTokens` default to `null` with `contextCapacityInvalid: false`; they are nullable positive integers that must be set together with the window larger than the reserve, both-cleared keeps a persisted invalid marker, malformed values are dropped (a valid sibling is kept), and partial/equal/reversed pairs keep their entered values and set the marker. The settings tab's **Context window (tokens)** and **Output reserve (tokens)** controls preview the pair immediately and persist on the input `change` event. ## Coding conventions

- Follow the existing TypeScript style: tabs for indentation, single quotes, semicolons, trailing commas where used, and `async`/`await` for asynchronous work.
- Keep strictness intact. `tsconfig.json` enables `strict`, `noImplicitReturns`, `noFallthroughCasesInSwitch`, `noUncheckedIndexedAccess`, `isolatedModules`, and consistent file-name casing. Handle possibly missing indexed values rather than suppressing these checks.
- Use Obsidian DOM helpers and `MarkdownRenderer`; keep user-facing copy short and in sentence case. Use the correct window's animation-frame APIs for popout compatibility and never inject model output with `innerHTML`.
- Register views, editor extensions, workspace events, commands, and other disposable resources through Obsidian's registration helpers so unload/reload cleans them up. Abort active chat and selection requests, close Web review, and cancel pending renders when their views close.
- Keep ordinary chat completions on the streaming `fetch` transport in `provider-stream.ts`. Do not reintroduce `requestUrl`, a second chat-completion stack, or silent retries. Provider-specific capabilities such as DeepSeek web retrieval must remain isolated in focused adapters with validated payloads and the shared credential-safe error policy; never copy their schemas to Kimi/custom requests.
- Use Obsidian CSS variables and the `emend-` CSS prefix for current UI. Update CSS classes and selectors together.
- Current public identifiers are plugin ID `emend`, view type `emend-chat-view`, chat command ID `emend:open-chat`, mode command IDs `emend:switch-to-ask-mode` / `emend:switch-to-edit-mode`, and selection command ID `emend:modify-selected-text`. Keep renames consistent and deliberate.
- Keep startup work limited and avoid unnecessary vault scans or background AI requests. Desktop-only APIs are permitted by the manifest, but current provider streaming needs only standard browser APIs.

## Security and privacy

- API keys are secrets stored in Obsidian SecretStorage, never in Emend's `data.json`. Legacy plaintext migrates on load, and every save writes empty provider `apiKey` fields. Never commit `data.json`, print keys, or include them in logs and error messages. Manual mock credentials must remain dummy values in ignored vault data.
- Read-only requests send bounded note content. Full-note Edit sends the complete note regardless of the context limit. Composer Selection sends the complete selection plus surrounding context and the originating session's configured recent ready history, never a truncated selection or another session's messages; the Command Palette Modify Selection modal sends the same complete context with no chat history. Default smart context can send complete containing/adjacent paragraphs, YAML frontmatter, or fenced code within the source-character budget; exact omission markers are additional. The opt-out sends Stage 09 symmetric before/after context. Explicitly selected additional notes use a separate combined source-character budget and are read-only in every mode. Prompts, originating-session recent ready chat history for full-note/read-only chat and composer-Selection requests (never the modal), selected additional-note snapshots, vault-root `AGENTS.md`, and directly referenced skills are sent to the selected provider only when the user submits. An Edit result's model-written summary is ordinary ready assistant content; it is never written into the note and is sent later only as normal history within that session's configured window. Picker/open/note/session-switch actions perform no additional-note content reads or provider requests; local aggregate saves perform no networking.
- Capacity window/reserve values and the invalid marker are ordinary non-secret local settings. The draft estimate is computed locally without provider calls, tokenizer downloads, pricing or model-metadata lookups, vault scans, or additional-note content reads, and it is never stored. Capacity guards reject an oversized request before networking and never compress, summarize, or truncate context to make it fit.
- Opted-in main Web model rounds send the same ordinary context/history/instructions to DeepSeek, which may derive search queries, fetch URLs, and extraction goals containing note-derived text. DeepSeek Search/Fetch endpoints receive only validated visible query/URL arguments; Review exposes and permits editing every target and goal. Each readable result invokes a same-provider/model extraction reader that receives the current typed question, extraction goal, target, and source catalog with empty history, but no note snapshot/path, instructions/skills, additional notes, or vault content; its verifier receives only the question, goal, and numbered claims with quotes. Disclose current-question sharing, extractor/verifier/refine rounds, possible separate charges, the single retry, and that failed calls count toward the configured call limit. Changing Web mode, opening/switching notes, loading threads, and rendering citations perform no retrieval. Kimi/custom and unsupported-model requests fail clearly with no silent unsearched fallback, automatic retry, or fallback provider.
- Retrieved text, extracted claims, and quoted evidence are untrusted external data. Canonical retrieval remains transient and available only through bounded local extractor grep/read tools; the main model receives only deterministic per-call-capped verified claims with their exact quotes or quotes-only evidence, never raw retrieval or a raw failure fallback. The verifier receives only the current question, extraction goal, and numbered claims with quotes, never canonical source text. Only successfully represented actual normalized credentialess HTTP(S) result URLs become deduplicated stable citations; render source snippets as text and never inject retrieved/model markup with `innerHTML`.
- Ready chats remain local under `<configDir>/emend/chats/` in schema-3 ordered per-note session aggregates, with schema 1/2 loading and lazy migration on the first valid mutation. Only the exact originating session receives provider history and completed results. Completed all-main+extractor+verifier+refine usage counts and their provider/estimated source, ready Review/Auto user badges, sanitized ready assistant citations, folded query/URL/outcome activity, main reasoning, and Edit results — header, target line, optional model-written summary, and sanitized bullets — may persist as ordinary ready content. The unread, extraction, search, cap-fitting omission, and skipped-call warnings are ordinary persisted content; activity failure reasons, reader failure kinds, failure HTTP statuses, and attempt counts are transient. Do not persist credentials, per-session drafts, unknown message artifacts, raw request bodies/tool arguments/results, retrieved content, extractor/verifier/refine payloads, evidence, reasoning, and rounds, transient Web activity or activity failure reasons, note or captured-selection snapshots/text/offsets, additional-note selections/snapshots/content, loading/error/stopped messages, or full edit responses. Session management and local title derivation make no provider calls; AI titles/summaries and note-rename migration are not implemented. Additional-note paths and transient sessions/drafts live only in memory for the current view/plugin session and clear on reload. Deleting a note does not automatically delete its aggregate. Preserve malformed data and never overwrite unsupported schema versions. Estimates are character-based, not provider billing data; do not invent retrieval, reader, or search pricing/token counts.
- The active and additional vault/note paths are sent only when **Include note path** is enabled. Local additional-note controls always display selected paths; path-off provider prompts use generic numbered labels without basenames or vault names, while path-on prompts use vault-qualified paths.
- Ask/Discuss/Brainstorm have no note writer, including during Web retrieval. Only the full-note Edit coordinator receives the guarded vault writer; selection coordination receives only the guarded native editor adapter. Web is unavailable to Edit, quick actions, and Modify Selection. Additional-note snapshots never become edit targets, and additional-note-only anchors fail with zero writes. Both write paths apply validated CriticMarkup immediately after completion and stale checks. Do not add writes outside these permission-gated paths or revive automatic legacy JSON edits.
- Do not add telemetry, remote code execution, automatic plugin downloads, or unrelated network calls. Keep current file access within the vault and limited to the active note, explicitly selected additional notes, local conversation threads, and declared instructions/skills.
- Preserve clear provider error handling without exposing request headers or credentials.

## Versioning and deployment

Use semantic versioning. Running:

```bash
npm version <patch|minor|major>
```

updates `package.json` through npm and invokes the `version` script, which copies `npm_package_version` into `manifest.json`, adds the version and current `minAppVersion` to `versions.json` if absent, and stages those two metadata files. Review the resulting changes rather than editing the files inconsistently.

For a release, create or dispatch a tag that exactly matches the manifest version, without a leading `v`. `.github/workflows/release.yaml` verifies the tag against `manifest.json`, runs clean install/lint/tests/build, and publishes `main.js`, `manifest.json`, and `styles.css` as individual GitHub release assets. Keep `minAppVersion` and the `versions.json` mapping accurate when adopting newer Obsidian APIs.

GitHub Actions runs lint, tests, and the production build through `.github/workflows/ci.yaml` on `ubuntu-latest` with Node 24. The release workflow uses `softprops/action-gh-release` with repository-scoped `contents: write` permission; CI uses `contents: read`. Verify the relevant GitHub run before publishing or merging.
